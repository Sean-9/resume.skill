# resume.skill — 简历生成、优化与定向迭代

> 简历上每多写一句，面试就多一道题。这个 skill 先确认哪些能写，再决定怎么写，最后模拟被问一遍。三道工序，顺序不能换。

---

## When to Use

- 用户想从零做一份简历，但说不清自己有什么经历
- 用户有旧简历，想按某个 JD 改一版
- 用户手里有项目报告、绩效自评、实习证明等零散材料，想整理成简历
- 用户说"简历投了没回音"、"HR 不看我简历"
- 用户是转行/跨专业，不知道过往经历怎么翻译成目标岗位的语言

---

## 核心设计原则（先读这一段）

这个 skill 和"AI 一键生成简历"的区别在于三道工序的**顺序**。顺序反了就变成"先编好看的，再想办法圆"。

### 工序一：证据闸门 —— 决定哪些能写

每条 bullet 必须能追溯到经历库里的原始素材 ID。追溯不上的**不生成**，标记 `[需你补充]` 交回用户。数字只能来自用户原话，模型不得推算、不得"合理估计"、不得把"快很多"升格成"提升 10 倍"。

宁可弱，不许虚。转行客户最大的风险不是简历不够漂亮，是漂亮到面试被问穿。

### 工序二：八秒排序 —— 决定怎么排、怎么说

HR 前 8 秒只会看到三样东西：姓名旁的一句话定位、最近一段经历的第一条 bullet、技能栏。把过闸的素材按"这三行能不能让人想约面"重排、强化动词、压紧表述。

**这一步只允许在闸门放行的素材池内操作，不得新增任何内容。**

### 工序三：压测 —— 决定能不能投

每条 bullet 生成 4 层追问链，模拟面试官顺着这句话往下刨。挂掉的打回工序一重写。`claimed` 级证据（有数字但说不清怎么测的）强制标红。

2. **读档检查**：检查 `./interview_saves/` 是否有该岗位的读档。有则读取其"能力维度框架"和"最弱维度"，在 Phase 4 取舍时优先突出弱维度以外的强项，并在差距清单里提示："你在 D3 指标感上模拟面试表现偏弱，简历里这块少写，别自己给自己挖坑。"

**Phase 8 交付后**：主动提示用户衔接下一步：

```

下一步建议：用 interview.skill 面一遍这个岗位，
它会读取刚才的经历库和追问清单，直接从简历上的
薄弱句子开始问。答不上来的，回来改简历。
```

### interview.skill 需要的一行改动

`interview.skill` 当前用 `./interview_saves/` 存读档，不读经历库。要接上本 skill，在其 **Step 0.5 读取读档之前**插入一步：

```
Step 0.4b — 读取经历库（如有）
检查 ./jobsearch/profile.md 是否存在
→ 存在：读取全部经历块，用于行为面命题。
        优先针对 metric_source 为 claimed 的素材出题——
        这些是用户简历上写了数字但说不清来源的地方，真面试最容易翻车。
        若同时存在 ./jobsearch/resumes/{slug}_压测清单.md，
        把清单里的追问链直接并入题库。
→ 不存在：按原流程走，行为面题从 JD 反推
```

未做这个改动时，本 skill 仍可独立运行，只是联动降级为"用户手动把 profile.md 贴给面试 skill"。

## Core Architecture: 四个 Agent 角色

| Agent | 角色名 | 职责 |
|---|---|---|
| 🎤 MINER | 挖掘官 | 从口述/旧简历/项目材料中提取经历，按五槽位追问补全，标注证据等级 |
| 🔒 GATEKEEPER | 闸门官 | 逐条素材过证据闸门，拦截无出处的表述和数字，产出可用素材池 |
| ✍️ WRITER | 撰稿官 | JD 匹配、取舍、八秒排序、动词强化，只在素材池内操作 |
| 🎯 STRESSER | 压测官 | 为每条 bullet 生成 4 层追问链，标红高风险表述，交接给 interview.skill |

## Phase Architecture

```
PHASE 0 ── 路由与读档
PHASE 1 ── 采集（MINER）············ 三入口 → profile.md
PHASE 2 ── JD 解析
PHASE 3 ── 证据闸门（GATEKEEPER）··· 工序一：哪些能写
PHASE 4 ── 匹配与取舍（WRITER）
PHASE 5 ── 八秒排序与改写（WRITER）· 工序二：怎么写
PHASE 6 ── 渲染
PHASE 7 ── 压测（STRESSER）········· 工序三：能不能投
PHASE 8 ── 交付与衔接
```

**强制时序**（任何情况下不得违反）：

1. Phase 3 未完成，不得进入 Phase 5 —— 不许边生成边判断证据
2. Phase 5 不得引入 Phase 3 素材池之外的任何内容
3. Phase 6 渲染由脚本完成，模型不直接排版
4. Phase 7 未完成，不得声称简历"可以投了"

## PHASE 0 — 路由与读档

### Step 0.1 — 判断入口

| 用户给了什么 | 走哪个入口 |
|---|---|
| 只说"帮我写简历"，没材料 | 入口 A：口述挖掘 |
| 上传/粘贴了旧简历 | 入口 B：反向解析 |
| 上传了项目报告、绩效自评、实习证明、课程设计 | 入口 C：材料提取 |
| 上传了 JD + 旧简历 | 入口 B，然后带 JD 走全流程 |

三个入口可叠加。用户先给旧简历再补口述，是最常见也最好的组合。

### Step 0.2 — 检查已有资产

```
检查 ./jobsearch/profile.md
→ 存在：展示摘要"已有 N 段经历、M 条素材，最近更新 {日期}。
        这次是补充新经历，还是直接按新 JD 生成一版？"
→ 不存在：进入 Phase 1

检查 ./interview_saves/
→ 存在同岗位读档：读取能力维度框架与最弱维度，记入本次上下文
```

**已有 profile.md 且用户只是要新岗位版本时，跳过 Phase 1 直接进 Phase 2。** 这是经历库存在的主要意义——第二次只用给 JD。

## PHASE 1 — MINER：采集

三个入口，统一写入 `./jobsearch/profile.md`。字段规范见同目录 `profile-schema.md`，采集前先读一遍。

### 入口 A：口述挖掘

用户口述一定会说"我负责了 XX 项目"，零信息量。用固定协议逼出细节。**每段经历五个槽位不填满，不许进入下一段。**

| 槽位 | 追问话术 | 填不满时 |
|---|---|---|
| context 场景 | 这事发生的时候，团队/业务处在什么状态？为什么要做这件事？ | 追问"如果不做会怎样" |
| action 动作 | 具体你做了什么？团队里别人做了什么？ | **强制拆分"我"和"我们"**，用户说"我们做了"必须追问"这里面哪部分是你" |
| decision 决策 | 中间有没有卡住过？你怎么选的？为什么不选另一条路？ | 追问"有没有走过弯路/返工过" |
| result 结果 | 做完之后，什么变了？现在还有人在用吗？ | 追问"如果你没做这件事，现在会是什么样" |
| metric 指标 | 有数字吗？没有的话——覆盖多少人？多久一次？以前多久现在多久？ | 降级为 proxy，不许硬凑 |

**decision 槽位是大部分简历工具没有的**，但它是面试官真正在意的东西，也是 Phase 7 追问链和 interview.skill 行为面题的原料。用户答不出决策的经历，通常说明他只是执行者，这条在 Phase 4 里要降权。

采集顺序：从最近的经历倒着问。用户说"没什么可写的"时，按这个顺序挖：正职 → 实习 → 课程项目/毕设 → 竞赛 → 社团/学生工作 → 自学项目 → 兼职。转行客户的可用素材通常藏在后四类里。

### 入口 B：旧简历反向解析

```
1. 逐条提取现有 bullet，写入 profile.md 的 items[]
2. 每条标注 metric_source（旧简历里的数字多半是 claimed 级）
3. 对每条问用户一次："这句话背后的具体动作和决策是什么？"
   —— 旧简历的 bullet 通常已经被压缩过，decision 槽位大概率是空的
4. raw 字段存旧简历原文
```

**不要直接拿旧简历的 bullet 当素材用。** 旧简历是加工过的产物，本 skill 需要的是加工前的原料。解析出来之后必须回填 context 和 decision。

### 入口 C：材料提取

支持：项目报告、绩效自评、实习证明、课程设计、论文、周报合集。

```
1. 通读材料，按时间/项目切分成经历块
2. 提取候选素材，每条标注在原文的位置
3. 生成"提取确认清单"给用户逐条判断：
   ✅ 确认 —— 这条是我做的，写进经历库
   ✏️ 修正 —— 材料写得不准，我来改
   ❌ 排除 —— 这是团队的，不是我的
4. 材料里的数字一律先标 claimed，除非材料本身说明了测量方式
```

### Step 1.x — 写入确认

每完成一段经历，展示结构化结果给用户确认，再写入文件。不要采集完十段一次性甩出来。

## PHASE 2 — JD 解析

无 JD 时跳过，生成通用版（Phase 4 取舍改为按"最强素材优先"）。

```markdown
## JD 解析：{公司} · {岗位}

| # | 要求原文 | 类型 | 权重 |
|---|---|---|---|
| R1 | {原文摘录} | 硬性/加分/隐含 | 高/中/低 |

**隐含职级**：{从"独立负责""带团队""协助"等措辞反推}
**行业黑话**：{JD 里出现的、简历中应当自然用上的领域词}
**真实痛点推测**：{这个岗位为什么招人——补人手？填能力空缺？新业务？}
```

JD 存档到 `./jobsearch/jd/{slug}.md`，供 interview.skill 复用。

## PHASE 3 — GATEKEEPER：证据闸门

工序一。逐条遍历 `profile.md` 的 items，输出可用素材池。

### 过闸规则

| 检查项 | 不通过时 |
|---|---|
| 有 action 且为第一人称 | 打回 Phase 1 补追问 |
| 数字能在 raw 或用户原话里精确匹配 | 剥离数字，降级为定性表述 |
| metric_source 已标注 | 标 none，禁止该条出现任何数字 |
| result 非空 | 标记 `[需你补充：这件事做完之后什么变了？]` |

### 证据等级与允许的写法

| 等级 | 定义 | 简历里允许怎么写 |
|---|---|---|
| `verified` | 有数字，且说得清怎么测的、基线是什么 | 直接写数字 |
| `claimed` | 有数字，说不清测量方式 | 可写，Phase 7 强制标红 |
| `proxy` | 无数字，有代理指标（覆盖人数、频次、前后时长对比） | **只能写代理指标本身，不许换算成百分比或倍数** |
| `none` | 什么都没有 | **禁止出现任何数字**，只能定性 |

### 输出

```markdown
## 素材池（Phase 3 输出）
| 素材 ID | 一句话 | 证据等级 | 可用 |
|---|---|---|---|
| EXP-03-2 | 配置化字段映射，换仪器免重写 | verified | ✅ |
| EXP-03-1 | 数据处理脚本，组内 6 人使用 | proxy | ✅ |
| EXP-02-1 | 用户增长提升 30% | claimed | ⚠️ 可用但压测标红 |

## 需你补充（不生成，等你回答）
- EXP-05-1：你写了"显著提升效率"，这个"显著"具体是什么？没有数字的话，
  以前做一次要多久、现在要多久？
```

**这一步要把"需你补充"清单当面给用户，不要静默降级。** 用户看到自己哪些经历说不清，本身就是有价值的反馈。

## PHASE 4 — WRITER：匹配与取舍

```markdown
## 匹配矩阵
| JD 要求 | 命中素材 | 匹配程度 |
|---|---|---|
| R1 熟悉数据处理流程 | EXP-03-1, EXP-03-2 | 🟢 硬命中 |
| R2 有跨部门协作经验 | EXP-01-3 | 🟡 可迁移 |
| R3 3 年以上产品经验 | — | 🔴 确实没有 |

## 取舍决策
- 主打：{哪两三段经历撑门面}
- 淡化：{哪些只留一行}
- 删除：{哪些完全不放}
- 章节顺序：{按职级和背景决定，如转行者把项目经历提到工作经历之前}
- 页数目标：{1 页 / 2 页}
```

取舍原则：**按匹配度排，不按时间排**。转行客户的最近一份工作往往和目标岗位无关，硬按倒序会把最弱的放最前。

🔴 确实没有的项目**如实保留在差距清单里**，不试图用相邻经历掩盖。这份清单是交付物的一部分。

## PHASE 5 — WRITER：八秒排序与改写

工序二。只在素材池内操作。

### 八秒扫描测试

写完后把简历压成 HR 前 8 秒能看到的三行，问自己："这三行能不能让人想约面？"

```
第 1 行：姓名 + 一句话定位（不是"求职意向"，是"我是谁、能干什么"）
第 2 行：最近一段经历的第一条 bullet
第 3 行：技能栏前半截
```

不过关就重排，而不是重写措辞。

### 改写规则

| 规则 | 说明 |
|---|---|
| 动词优先级 | 主导/设计/搭建 > 负责/参与/协助。**但只有 decision 槽位非空的素材才配用主导类动词** |
| 结构 | 动作 + 方法 + 结果，一句话讲完，不超过两行 |
| 关键词 | JD 黑话要出现，但用用户自己的经历语言表达，不生搬 JD 原句 |
| 禁止 | 形容词堆砌（"高效""优秀""深入"）、无主语句、"负责相关工作" |

### 硬校验（Phase 5 结束前必须跑）

```
草案里出现的每一个数字 → 回 profile.md 精确匹配
匹配不上 → 立刻删除该数字，不解释、不商量、不"重新推导"
```

这是本 skill 最常见的失效点。模型在追求表达效果时会自发补数字。

## PHASE 6 — 渲染

模型生成结构化 JSON，由脚本渲染，不直接排版。

```
scripts/render.py      JSON → docx（python-docx，模板 assets/template.docx）
scripts/to_pdf.sh      docx → pdf（libreoffice --headless --convert-to pdf）
scripts/to_text.py     JSON → 纯文本（BOSS 直聘等平台粘贴用，去掉所有格式符号）
schema/resume.schema.json
assets/NotoSansCJKsc-Regular.otf
```

四种格式全部产出。纯文本版单独优化：无表格、无制表符、段落间空行分隔，直接粘贴不乱。

v1 只有一套排版模板。

## PHASE 7 — STRESSER：压测

工序三。为每条 bullet 生成 4 层追问链。

### 追问链模板

| 层 | 追问方向 | 答不出说明什么 |
|---|---|---|
| 1 数字来源 | 这个数字怎么测的？基线是哪次？ | 数字是拍的 → 改成不带数字的写法 |
| 2 决策归属 | 这事之前为什么没人做？是没人想到还是有别的约束？ | 你只是执行 → 这条降权，不该放第一条 |
| 3 边界条件 | 如果 {关键前提} 变了，你做的东西会怎样？ | 你做的是一次性方案 → 措辞要改 |
| 4 持续性 | 这个东西现在还有人用吗？ | 结果部分要重写 |

### 输出

写入 `./jobsearch/resumes/{slug}_压测清单.md`：

```markdown
# 压测清单：{公司} · {岗位}

## ⚠️ 高风险表述（claimed 级，优先处理）
### bullet 3：「用户增长提升 30%」← 素材 EXP-02-1
- Q1 这个 30% 是怎么算的？和哪个时间段比？
- Q2 同期有没有其他因素也在推增长？你怎么归因到自己头上的？
- 建议：答不上来就改成「主导 XX 功能上线，覆盖 X 类用户」，去掉百分比

## 常规追问
### bullet 1：「设计配置化字段映射，换仪器适配从 2 天降到 10 分钟」
- Q1 ...
```

**判定规则**：4 层挂 2 层及以上，这条 bullet 视为虚的，打回 Phase 5 重写；4 层全过，这条前移。

### 衔接提示

## Common Pitfalls

### 1. 模型偷偷补数字
❌ 用户说"快很多"，简历写成"效率提升 10 倍"
✅ Phase 5 硬校验：每个数字回 profile.md 精确匹配，匹配不上直接删

### 2. "我们"污染
❌ 采集时不拦，写进简历全是团队功劳，面试一问就露
✅ Phase 1 强制拆分，用户说"我们做了"必须追问"哪部分是你"

### 3. PDF 中文变方块
❌ 依赖系统字体，导出后中文全是口口
✅ Noto Sans CJK 打包进 skill 的 assets/，渲染时显式指定

### 4. 直接拿旧简历 bullet 当素材
❌ 旧简历是加工过的产物，decision 和 context 都丢了
✅ 入口 B 必须回填场景和决策，把加工品还原成原料

### 5. JD 关键词硬塞
❌ 为了匹配把 JD 原句生搬进 bullet，读起来不像人话
✅ 关键词要有，但用用户自己的经历语言表达

### 6. 按时间倒序排经历
❌ 转行客户最近一份工作往往最不相关，倒序把最弱的放最前
✅ Phase 4 按匹配度排

### 7. 只交简历文件
❌ 只给 docx，免费工具也能给
✅ 修改说明表 + 差距清单 + 压测清单，这三份才是用户学得到东西的部分

### 8. 跳过 Phase 7 就说"可以投了"
❌ 简历生成完直接交付
✅ 压测是交付的必要条件，不是可选增值项

## EXTEND.md 扩展建议

用户可在同目录创建 `EXTEND.md` 添加：

- 自定义排版模板路径（替换 assets/template.docx）
- 目标行业的专属措辞规范（金融/互联网/制造用词差异很大）
- 个人固定信息（联系方式、GitHub、作品集链接）
- 常投岗位类型，用于 Phase 4 取舍时的默认偏好
- 经历库与输出目录的自定义路径
- 禁用词表（用户不希望出现在自己简历里的词）
